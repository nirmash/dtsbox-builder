# DTS + dtsbox Concepts (Distilled)

This is the concept reference the `dtsbox-builder` skill draws on. The full programming model is
in [`dts-sandbox-poc/docs/programming-model.md`](https://github.com/nirmash/dts-sandbox-poc/blob/main/docs/programming-model.md).

## The One-Liner

`dtsbox` is a thin CLI harness around Azure Durable Task Scheduler (DTS) and Container Apps
SandboxGroups. It gives you durable orchestration (workflows survive crashes, reboots, timeouts)
plus isolated execution for every step.

## The Five Building Blocks

**Orchestrator** — Deterministic Python function (`@dtsbox.orchestrator`) that says **what** to do
and in what order. Lives in `orchestrators/{name}.py`. DTS replays it from history on every crash,
so it must never call `time.now()`, `random()`, or do I/O directly.

**Activity** — Function (`@dtsbox.activity`) that does the actual work. Lives in
`activities/{name}.py`. Typically calls `dtsbox.run_sandbox_step(ctx, ...)` to allocate an ephemeral
sandbox, run code, capture stdout, and delete the sandbox. Runs exactly once per scheduled task —
no replay, side effects allowed.

**Sandbox source** — Declared in `dtsbox.yaml` under `sources:`. Three types:
- `type: code` — inject Python source into a public disk image (e.g. `image: python-3.12`)
- `type: image` — boot from a private disk image (`disk_id: /subscriptions/.../diskImages/abc`)
- `type: snapshot` — restore from a captured sandbox state (`snapshot_id: ...`)

All three use the same activity API: `dtsbox.run_sandbox_step(ctx, source="<key>", command="...")`.

**Worker** — Long-lived process (local during dev, ACA container in Azure). On startup,
auto-discovers `orchestrators/` and `activities/`, registers them with DTS, then pulls work via
gRPC. No manual `worker.py` editing — it's auto-generated by `dtsbox publish`.

**Scheduler (DTS)** — Azure-managed Durable Task Scheduler. Holds the work queue, persists history,
ensures exactly-once semantics. The cleanup singleton (an eternal orchestrator) GCs orphaned
sandboxes every N minutes.

## Replay — The Core Invariant

When the orchestrator yields a task and the worker crashes, DTS restarts the orchestrator from the
top. Already-completed `ctx.call_activity(...)` calls return cached results from history; new ones
get scheduled. **The orchestrator must produce the same calls in the same order every time.**

That's why:
- Orchestrators never call `time.now()` or `random()` — they'd get different values on replay
- Orchestrators never do network/file I/O — those would re-execute on every replay
- Activities are where all side effects live — they're called from the orchestrator but run once

## Lifecycle of a Run

User runs: `dtsbox run my_workflow --input '[1,2,3]'`

1. CLI sends `start_orchestration` to DTS
2. Worker pulls the instance, runs the orchestrator function
3. Orchestrator schedules N activity tasks via `ctx.call_activity(...)`
4. Orchestrator yields `task.when_all(tasks)` — checkpoints, suspends
5. DTS dispatches activity tasks to workers (parallel if multiple replicas)
6. Each activity boots a sandbox, runs the command, captures stdout, deletes the sandbox
7. When all activities complete, DTS wakes the orchestrator (replays history up to the yield, then
   resumes after it)
8. Orchestrator aggregates results, returns final value
9. DTS marks the orchestration `COMPLETED`; user runs `dtsbox logs <id>` to see the result

## How Code Connects to YAML

| YAML field | Read by | Effect |
|---|---|---|
| `sources.<name>.{type, image, disk_id, snapshot_id, timeout_seconds}` | `dtsbox/sandbox.py` | Passed to Azure SDK `begin_create_sandbox()` |
| `cleanup.grace_minutes` | `dtsbox/cron.py` | Cleanup activity threshold and loop interval |
| `azure.dts_endpoint` | `dtsbox/runtime.py` | Worker gRPC connection to DTS scheduler |
| `schedules.<name>.{workflow, cron, input}` | `dtsbox/runtime.py` | Starts eternal orchestrator on worker boot |
| `workflows.<name>.eternal: true` | `dtsbox/runtime.py` | Auto-starts singleton on worker boot |

## The Simplifying Rule

- **Orchestrators are deterministic and cheap** — they're replayed, so never side-effect inside them
- **Activities are where side effects happen** — run once, succeed or fail, no replay
- **Sandboxes are ephemeral per-step** — created, used, deleted; no state survives between activities

## Common Questions

**Why must orchestrators be deterministic?**
DTS replays them from history on every crash. Non-determinism breaks the replay contract.

**Where do I put my actual work code?**
In activities. Orchestrators are for control flow and aggregation. Activities query databases, call
APIs, and run computations — typically inside an ephemeral sandbox.

**Can I run multiple orchestrators in one project?**
Yes. Drop multiple files in `orchestrators/`. Auto-discovery finds them. Invoke independently with
`dtsbox run <name>`.

**What if a sandbox crashes mid-activity?**
It's orphaned. The cleanup singleton GCs it within `cleanup.grace_minutes` (default 5).

**Can I use container images directly?**
Not as a sandbox source. Build a disk image first (`begin_create_disk_image(<acr-image-uri>)`),
then reference its resource ID in `dtsbox.yaml` as `type: image`.
